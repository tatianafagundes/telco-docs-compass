# TMF API rules

- TMF667 API for connected systems: routes under `src/routes/api/public/tmf-api/document/v4/` (and the legacy `documentManagement/v4/`) are thin; logic is in the `src/services/gateway-*.ts` files, listed in `src/services/tmf-gateway.ts` (system-key check first, every query pinned to the key's tenant) and pure mapping in `src/services/tmf667-mapper.ts` (tested). Keys are stored hashed in `integration_clients`; events come from a `documents` trigger into `event_outbox`, delivered by the scheduled `/api/public/tmf-events/deliver`. Why: other systems get the same rules as the screens without ever touching a person's session.
- TMF API routes spread `otherMethods([...])` into their handlers and `src/routes/api/public/tmf-api/$.ts` catches unknown paths, so systems always get TMF JSON (405/404), never the app page. Regression: `e2e/tmf-api.py` (Playwright + HTTP, exits 1 on failure). Why: unhandled methods otherwise answer 200 HTML.
- TMF667 v4: standard routes in `src/routes/api/public/tmf-api/document/v4/`; `documentManagement/v4/` is a legacy alias wrapped in `legacy()`. Internal `lifecycleState` is the source; v4 `status`, event names and SID types are derived in `tmf667-mapper.ts` (tested); extensions declared via `@type EradDocument` + `public/tmf-schemas/`. Why: standard clients work while old integrations keep their shapes.
- API security lives in the `gateway-*.ts` files (`gateway-core.ts`, `gateway-token.ts`, `gateway-body.ts`, `gateway-fetch.ts`): per-system limits (`integration_clients` columns, pure rules in `src/services/rate-limit-rules.ts`, regression `e2e/tmf-rate-isolation.py`), key `expires_at`, hashed OAuth tokens, DNS-checked URLs, events signed over "<ts>.<body>". Why: TMF630 guidance without new libraries.
- Event delivery: outbox rows fan out to one `event_deliveries` row per matching same-tenant subscription; passes claim rows with `claim_event_deliveries` (SKIP LOCKED) and retry per subscriber; pure rules in `src/services/event-delivery-rules.ts` (tested); regression `e2e/tmf-events.py` (helper `e2e/events-helper.ts`). Why: one failing subscriber must never cause duplicates for others or for overlapping passes.
- API four-eyes: documents registered over the API store `registered_by_client`; approval by that same key is refused (`systemMayApprove` in `document-rules.ts`). Bulk passes emit one `DocumentBatchEvent` (`recordBatchEvent` in `bulk-worker.ts`), routed only to subscriptions naming it. Why: same separation of duties as the app, without flooding per-document subscribers.
- File hooks (`.kiro/specs/file-hooks`): `scanResult` (scope `scan`), `extractionResult` (scope `extract`) and `uploaded` (scope `register`, the registering system) are in `gateway-file-results.ts` and `gateway-file-upload.ts`. A processing key has that one scope and must be the organisation's designated system (checked in `authenticate`); answers are idempotent per document, version and attempt, checked in the order of R2.3, and write nothing when refused. Downloads use `downloadDecision` (`file-hook-download.ts`); never widen `read` routes to accept `scan` or `extract` except the attachment download. Files received with a request go through `processAsSystem`, never straight to `ready`. Why: the organisation's own antivirus decides, and a refused or late answer must never move a document.
