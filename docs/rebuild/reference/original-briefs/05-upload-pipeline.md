# Prompt 05 – Screen 3: upload and processing pipeline

Read AGENTS.md and docs/ui-references.md (patterns 10–12; Drive 5565311f, Sana 3b284428 as the anti-pattern, WeTransfer aca142ff). Plan first (5 lines), wait for OK.

Build "Add documents" on the entity Documents tab.

1. **Entry points:** the "Add documents" button, drag-and-drop anywhere on the tab (a full-tab drop overlay "Drop to add to O-7731" – short entity id), and paste. Multi-file. No page change. Prevent the browser's default drop **everywhere in the app**: a drop outside a Documents tab does nothing except show "Open an order's Documents tab to add files" (otherwise the browser opens the PDF and the user leaves the app).
2. **Dialog** (572px) lists each file as a row: name (middle-truncated, extension kept), size, document type, and required metadata for that type (from the effective specification; required marked with `aria-required`, never an asterisk alone). **Default type:** on an order, "Order attachment"; on an account, "Contract" only if the file name contains a contract word, otherwise "Order attachment"; never default to a type whose required fields the user must type, and show why the type was chosen ("Based on: added to an order"). Validation per file: unsupported type, too large (limit from specification), duplicate name on this entity (warn, offer "Add as new version of <doc>"). Helper line under the title: "Prototype: do not add real customer files." Buttons: default "Cancel", primary "Add N documents".
3. **Processing:** on confirm call `register` (Idempotency-Key per file), upload to Storage with the ticket, then show each file as a row at the top of the table immediately. The Pipeline tag goes Uploading → Scanning → Reading → **Ready**; a "Ready" tag (tone `cleared`, check icon and the word) **stays visible on rows added in this visit until the user leaves this entity's Documents tab**, so people see the end state instead of the absence of a tag. Lifecycle Status for new files is Draft; the tooltip on Draft says "Not reviewed yet. People with access to this order can already open it." A collapsible toast "Adding 3 documents" shows per-file state. Its progress bar covers **upload only** and is labelled "Uploaded – checking files…"; it never shows 100 % while any file is still being checked. When every file has finished, the toast's final line reads "3 added: 2 ready, 1 needs attention" and stays until dismissed. Announce only the batch's final state in an `aria-live="polite"` region ("3 files added. 2 ready, 1 needs attention."), not every step of every file. Processing tooltip: "Scan is simulated in this prototype."
4. **Errors** (reasonKey → sentence map; never "Unknown error"):
   - Upload failed (network): "Upload stopped at 62 %. Nothing was added. Try again." with Retry.
   - Quarantined: row tag "Quarantined", cause "The security scan found a threat in this file. It was blocked and cannot be opened or downloaded." Actions: Delete, "Report to security" (seam `reportProblem` kind security; confirms "Reported to security. They will contact you if they need more."). No Download anywhere.
   - Failed reading: "We couldn't read the text in this file, so no details were filled in." Actions: Keep without reading, Retry, Delete. **Keep without reading** (seam `updateMetadata` with `keepUnread: true`) sets Processing to Ready with the note "Not read. Enter the details by hand."; it stays Draft and has no extraction. Retry is offered once; if it fails again: "Retrying won't help with this file. Keep it without reading, or delete it and ask for a clearer copy."
   - Group multiple errors in the toast ("2 of 5 need attention") with a link that filters the table to those rows – do not list repeated lines.
5. Retry only the failed files from the toast ("Retry 2 failed"), never the whole batch. Cancel per file while uploading. Pause is not needed. Use the verb **Delete** everywhere (recoverable, with Undo), never "Remove".
6. **Test hooks** (prototype, defined in prompt 02): a file containing the marker `TEST-QUARANTINE` (or named *.exe) is quarantined; a file containing `TEST-UNREADABLE` fails at reading, and fails again on Retry; anything else reaches Ready. Ready-made files are in lovable-kit/test-files/. Seeded documents never change pipeline state on their own.
7. Roles: viewer cannot add; contributor and above can; hold or retention do not affect adding.

States to verify: 1 file, 12 files, 100 MB file over limit, wrong type, duplicate, offline, quarantine, failed reading, retry that fails again, keep without reading, cancel, all-success, drop outside the tab. Verify at 1440 and 1920, light and dark, at 200 % zoom, keyboard (the drop zone must also work via the button), and report in one line.
