# Prompt 10 – Tenants and master tenant: configuration with inheritance, master view

Read AGENTS.md, contracts/model/tenant-policy.schema.json, docs/ui-references.md (Google Workspace Inherited/Overridden model, Snowflake account switcher 41e8b27f, Shopify unsaved bar fc31e4d8). Definition (confirmed by the product owner): "Master tenant" is a parent that owns shared configuration; child tenants inherit, extend, override or are locked. Plan first, wait for OK.

Admin area (left nav "Admin"), visible to tenant_admin and master_admin.

1. **Document types** page: table of effective specifications (from `listSpecifications`): Name, Code, Where defined (one triad everywhere in the UI, with the real organisation name and never the words master or tenant: **"From Aurora Telecom Group"**, **"Changed here"**, **"Locked by Aurora Telecom Group"**), Retention policy, Signature required, Review required, Contains personal data, Business process (GB921 code and name, for example "1.12.9.5 Negotiate Sales/Contract", read-only text from the specification's `businessProcess` with the release "GB921 26.0.0" shown in a tooltip). Row opens a 356px panel: all settings; each setting shows the same triad ("From Aurora Telecom Group" / "Changed here" / "Locked by Aurora Telecom Group"), read from `effective_specifications.overridden_fields`. A child admin can: add a new type, extend a type's characteristics (if mode allows), override an unlocked type's settings. Locked items are visible and read-only with the reason "Locked by Aurora Telecom Group". "Reset to master" on overridden items. Unsaved changes use one bar at the top: "Unsaved changes – Discard / Save". Saving writes through the edge function; changes below a master **hard floor** (min retention, auto-accept confidence, malware scan) are rejected with a sentence naming the floor ("Retention cannot be shorter than 6 years. Set by Aurora Telecom Group.").
2. **Policies** page: cards "Retention", "Sensitivity labels", "Access roles", "Confidence levels", "Approval steps", "Where files are stored" – each showing how this organisation relates to the group's setting in one sentence ("Uses the group's setting", "Adds its own", "Replaces the group's", "Locked by the group").
3. **Master tenant view** (master_admin only): a "Tenants" page listing child tenants with **counts only** from `master_document_stats` (documents by type, status, pipeline state), configuration diffs ("Aurora Mobile Sweden overrides 1 type, adds 0"), and the isolation settings. There is NO document list, name or content for children. The page says: "You see counts and settings. Document names and content stay inside each tenant." Master admins can edit master-owned definitions (including locking) and see which children use them.
4. **Context switching**: users belong to one tenant; the user menu shows tenant name and role. A master_admin gets a "Tenants" submenu to view a child tenant's configuration and counts (read-only), with a clear banner "Viewing Aurora Mobile Sweden as Aurora Telecom Group – counts and settings only".
5. **Change impact**: when a master edits a shared definition, show "Applies to 2 tenants. 1 tenant has overridden this and keeps its version." before saving.

Rules: tenant from the signed token only; no cross-tenant document access; every config change writes an audit event (who, what setting, from→to); hard floors and locks enforced server-side as well.

States: child admin with everything inherited, with overrides, master with no children, locked everywhere, save rejected by a floor, read-only role.

Verify at 1440 and 1920, light and dark, as master.admin, se.admin, se.viewer (no Admin), and report in one line.
